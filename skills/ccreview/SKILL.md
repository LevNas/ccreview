# ccreview — merge-time gate (prototype)

The design decisions are summarized in `${CLAUDE_PLUGIN_ROOT}/docs/decisions.ja.md` (Japanese). Labels in these steps such as "decision N" or "e2e D5" point there ("decision N" is the heading "決定 N"). You do not need to read it to follow the steps; read the entry only when you want the reason behind a label.
This skill holds only the main session's steps. The review and fix loop runs in the plugin's workflow `ccreview:ccreview-loop` (`${CLAUDE_PLUGIN_ROOT}/workflows/ccreview-loop.js`). The skill (`ccreview:ccreview`) and the workflow share one namespace, so they have different names (with the same name, the workflow hides the skill).
The fix agent's (type `ccreview:ccreview-fixer`) Bash and edits are held to a per-run allowlist by the plugin's PreToolUse hook (`${CLAUDE_PLUGIN_ROOT}/hooks/gate.py`) (decisions 21 and 24).

## What this skill does not do

- It posts to the MR/PR only when the user explicitly says so. It never uses `/code-review --comment`.
  - Post with gh or glab. If the loaded instructions (CLAUDE.md and the like) name a wrapper to use instead of glab, use that.
  - If authentication has expired, do not try to authenticate; tell the user and wait.
- It does not push or merge. A person gives the final approval.
- It does not touch main. Fix commits go only onto the target branch, checked out in an isolated worktree.
- The main session writes only the files these steps name (the `<diffDir>` of step 1, the allowlist of step 3, and the workflow result and comment draft, written to temporary files outside the repository). The checkout and worktree creation of step 1, and git operations, are separate. It never writes to the shared checkout outside the worktree (decision 29; in e2e D2 the main session tried to `cp` a correction plan there, and `cp` is not git, so the worktree check did not catch it).
- It does not save the result as a plan or task unasked. Whether to keep it, and where (an issue tracker, a task system), is the user's call; when asked, write it where the user says.

## Steps

1. **Pick the target**
   - Work in an isolated worktree (EnterWorktree; if already in a worktree, stay there).
   - For a PR number, look up the branches with `gh pr view <n> --json headRefName,baseRefName` and check it out with `gh pr checkout <n>`. For a branch name, check it out as is.
   - After `git fetch origin`, get the start SHA with `git merge-base origin/<base> HEAD` (the base defaults to `main`) and set the range to `<start SHA>..HEAD`. Never use the local `main` (if it is stale, unrelated changes fall into the range; decision 14).
   - Take the changed files with `git -c core.quotepath=off diff --name-only <range>`. Without `core.quotepath=off`, non-ASCII names come back as `"\343..."` and no longer match the gates' `paths`.
   - Let git write the diff to a file. Take the output of `git rev-parse --show-toplevel`, append `/.ccreview`, and use that absolute path as `<diffDir>` in every later step (so it names the same file whatever an agent's cwd is). Run `mkdir <diffDir>`, then `git diff <range> --output=<diffDir>/diff-r1.patch` (git does not create the folder). The perspective agents cannot run git, so they Read this file (decisions 16 and 26).
   - Do not add `-p` to `mkdir`. If `<diffDir>` already exists, `mkdir` fails; stop there and tell the user. If it is left over from an earlier run, remove it with `write_allowlist.py --remove --diff-dir <diffDir>` and start again. If the change itself contains `.ccreview`, stop whatever the trust level: a symbolic link named `.ccreview/diff-r1.patch` in the change would make `--output` overwrite its target (even outside the worktree).
   - Never copy the diff text into args. A model copying it can break it (in e2e session B, a diff the fix agent copied was broken by double escaping, and the reviewers of rounds 2 and 3 read the broken diff). Leave `<diffDir>` untracked; step 6 removes it.
   - **Decide the trust level (decision 18).** It is `trusted` or `untrusted`; there is no default.
     - If the user states it, follow that.
     - Otherwise, a PR number is `trusted` only when `gh pr view <n> --json author --jq .author.login` equals `gh api user --jq .login`. A local branch name the user gave is also `trusted`.
     - Everything else (someone else's PR, a fork, an MR whose author cannot be checked) is `untrusted`.
     - Show the user the decision and its grounds first.
2. **Read the declarations**
   - When `untrusted`, read `.claude/review-gates.yaml` and `REVIEW.md` from the base with `git show origin/<base>:<path>`, not from the working tree, so the PR cannot weaken the gates or perspectives by rewriting them. If they are missing on the base, stop and tell the user.
   - Read `.claude/review-gates.yaml`. Keep a gate that has `paths` only when a changed file matches one of its globs. `paths` is not read for a `pr-body` gate: it runs whenever the target is a GitHub PR.
   - Replace `{files}` in each command gate's `run` with the matching changed files (space-separated).
   - Also keep the `run` before expansion, as `template` (the allowlist of step 3 uses it to protect the gate's scripts).
   - From `REVIEW.md`, take the bodies of the sections "Severity definitions", "Category vocabulary" and "Rules for every perspective" (the Japanese headings "重大度の定義", "category の語彙" and "観点共通の決まり" are accepted too), and the vocabulary list (the words in backticks in the category section). Match the headings ignoring case and surrounding spaces; each section may use either language (decision 44). If any of the three sections is missing, or the vocabulary list is empty, stop and tell the user which; do not start the workflow with empty text. Give each perspective gate the body of its `ref` section as `sectionText`. Pass `passes` as the yaml gives it (1 when omitted).
   - **Run the command gates here** (the pre-check). Run each `run` at the repository root and collect `{id, exitCode, outputTail (about the last 40 lines), failures}`. `failures` are the per-file failures you can read from the output (path, line, summary), or empty if you cannot. Starting an agent inside the workflow for a command costs about 20k tokens or more each.
   - When `untrusted`, do not run the command gates. The command and the scripts it calls are part of the PR, so running them runs the PR's code. Leave `commandResults` empty.
   - **PR body gates (`kind: pr-body`, decision 45)** are run here, in the main session, and are never passed to the workflow (it stops at start on a kind it does not run). For each, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/check_pr_body.py --pr <n> --repo '<owner/name>' --id '<id>' --require '<names>'` with one `--require` per item of the gate's `require` (each item is heading names separated by `|`). Keep its JSON line and exit code for step 5. The script is ccreview's own and reads the body as data, so run it whether `trusted` or `untrusted`. It checks only that each section is there and not empty, not whether what it says is true; the rules (ATX headings only, comments removed, a child's text not counting for its parent) are in the script's docstring.
     - Take `<owner/name>` from the PR itself (`gh pr view <n> --json url`), so a fork or a checkout with several remotes cannot point the check at another PR with the same number.
     - Put every value in single quotes. If an `id` or `require` value contains a single quote, a backtick or a newline, do not run it; report the gate as not run, with that reason.
     - It reads GitHub PRs only. For a GitLab MR, or a branch with no PR, do not run it; step 5 reports it as "not run" with the reason. This does not change the verdict.
     - Exit code 2 (a `gh` failure, a body over the size limit, a usage error) means it could not check.
3. **Write the fix agent's allowlist** (only when `trusted`; with `untrusted` the fix agent does not run, so skip this)
   - Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/write_allowlist.py --range <range> --max-rounds <maxRounds> --diff-dir <diffDir> --gates '<json>'`. `--gates` is the command gates as `[{id, run (expanded), template (before expansion), blocking}]`.
   - The allowlist is written to the worktree's git dir (`<git rev-parse --absolute-git-dir>/ccreview/allowlist.json`). It is outside the working tree, so the fix agent cannot rewrite it. It holds the range's changed files, the read-only git commands, `git diff <range>`, `git diff <range> --output=<diffDir>/diff-r<N>.patch` for the next round's diff (N from 2 to maxRounds; the last round does not fix, so nothing beyond it is needed), each round's commit message, the command gates allowed to run, the gates' scripts (protected files), and an expiry (6 hours).
   - **Decision 23**: the script checks the command gates against the `ask` / `deny` rules of the effective settings (managed, user, project, local). A gate that matches one, or that contains shell metacharacters (`&&`, `|`, redirection and so on), is left out of the allowlist and returned in the output's `deferred` with the reason. A background fix agent that hits an `ask` rule waits until a person comes (the hook's `allow` loses to an `ask` rule).
   - Pass the output's `deferred` as is in `args.deferredGates`. If there are `settingsErrors` (the settings could not be read), every gate is deferred. Tell the user.
   - **Decision 31**: if the range has files under `.claude/` (other than `.claude/worktrees/`), tell the user before starting. When the fix agent edits one, it goes through Claude Code's protected-path check. Settings allow rules cannot lift it (official documentation), and the hook's `allow` did not lift it either (e2e D1; not documented). In manual and acceptEdits, a prompt appears for the background fix agent's edit and the run waits until the user answers. In auto, the classifier decides. In dontAsk the edit is denied, and the fix agent skips that finding and commits fixes for the rest (if every edit is denied there is no commit and it stops with `fail`). In bypassPermissions it goes through.
4. **Start the workflow**
   - Just before starting, record `git rev-parse HEAD` (step 5's check uses it).
   - `Workflow({name: "ccreview:ccreview-loop", args})`. Only when `trusted` and the name is not found, start it with `Workflow({scriptPath: "${CLAUDE_PLUGIN_ROOT}/workflows/ccreview-loop.js", args})`.
   - When `untrusted`, start it by name; if it is not found, stop and tell the user. Never use a `scriptPath` in the working tree (on a PR that changes ccreview itself, that would be the PR's version).
   - args: `{ range, changedFiles, diffDir: "<diffDir>", maxRounds, trust, gates (without `pr-body` gates), review: { severityText, categoriesText, categories, commonText }, commandResults, deferredGates }` (without `trust` the workflow stops at start).
   - The perspective agents give their own findings a severity and a category. The classifier agent is used only for findings without them (an optional `kind: review` gate and the like) (decision 12).
   - The perspective agents also give each finding its source (`origin`). They decide by asking "if this change were reverted, would this problem remain in exactly the same form?"; if it would, it is `pre-existing`. `pre-existing` findings are used neither for the verdict nor for fixing (decision 33). Findings with no value or an unknown value, and findings from gates other than perspectives, count toward the verdict.
   - The perspective and classifier agents run as the plugin type `ccreview:ccreview-reviewer` (Read, Grep and Glob only, `omitClaudeMd`). Without Bash they cannot run the change's code (decision 16; in the e2e runs, a ban in the prompt was not obeyed). From round 2 on, the fix agent writes the diff after its commit with `git diff <range> --output=<diffDir>/diff-r<next round>.patch`, and the next round's reviewers read it.
   - Types and hooks load when a session starts (start the run in a session started with the plugin loaded). If the type is not found, the perspective gates stop with `indeterminate` (they never fall back to a type with Bash).
   - Inside the workflow only the fix agent has Bash, and the hook holds it to the allowlist: one command per call, and edits only to the range's changed files. Some files stay protected even when the range changed them; the main ones are `.git`, settings, hooks, agent types, workflows, skills, `.claude/rules/` and `CLAUDE.md` at any level, the root `REVIEW.md` and `.claude/review-gates.yaml`, and the gates' scripts. Protected files are set in three places: fixed paths in `PROTECTED_SEGMENTS` and `PROTECTED_GLOBS` of `hooks/gate.py`, the scripts the command gates run in the per-run allowlist's `protected` (made by `scripts/write_allowlist.py`), and the ccreview plugin's own directory, refused separately by `edit()` in `gate.py`. Findings on them come back to the main session in the fix agent's `skipped` and the result's `remaining` (decision 32). Running code is not allowed. Anything off the list comes back as a `deny` with a reason, and the background run does not stop. After its commit, the fix agent runs the command gates that are not deferred. With `untrusted`, the workflow starts neither the fix agent nor the command gates and reviews with the read-only reviewers only (decision 18). Any blocking finding gives `fail`; with none, a blocking command gate that was not run gives `indeterminate`.
   - **Decision 25**: from the second time on, the command gates are run and reported by the fix agent after its commit. Gates in `deferredGates`, and gates whose report is missing, are not run by an agent in the workflow; they become "deferred" (the result's `deferred`). Deferral does not stop the loop. But if a blocking deferred gate remains where the verdict would be `pass`, the verdict is `indeterminate` ("deferred to the main session").
   - `maxRounds` is the yaml's `max_rounds` (the user's value, if given, wins).
   - **Receive the result (decision 42)**: when the run ends, a task-completion notification arrives. Its `<result>` can be cut off (in e2e D8, after the first 8,000 characters, "`... (truncated 10741 chars, full result in <file>)`"). Pass the notification's `<output-file>` absolute path as is to the command below. Use neither `cd` nor a relative path, and do not build your own way of reading it (in e2e D8, after misreading the shape, a compound command with `cd` stopped at a permission prompt and waited until the user came back).
     `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/extract_result.py --output <absolute path of output-file> --out <absolute path of a temporary file outside the repository>`
     - Run it inside the worktree under review. Whether `--out` is inside the repository is judged by the repository it runs in.
     - `--out` is, for example, `ccreview-result.json` under the session's scratchpad (or under `/tmp` if there is none). Pass the same path to `--result <result>` in step 5's check.
     - It writes the workflow's return value (the `result` key) in the output file to `--out` and prints only a summary of counts. In step 5, Read the `--out` file.
     - Exit code 2 means nothing was written: the shape is wrong, a path is relative, or `--out` is inside the repository, equals `--output` or cannot be written. Tell the user the printed reason; do not work around it by building your own way of reading.
5. **Report the result**
   - Summarize the `verdict` (pass / fail / indeterminate), the `stopReason`, and each round's failing keys and fix commits.
   - **Comment draft language** (decision 44): if the user or the loaded instructions name a language for the comment, use it. Otherwise the body of the severity section of `REVIEW.md` decides it: Japanese when that body is written in Japanese, English otherwise (headings and the other sections do not count, so a mixed file still gives one answer). The fixed sentences and the section headings below are given in both; use the ones in that language word for word.
     - "Remaining findings (blocking the merge)" / 「残った指摘（マージを止めるもの）」
     - "In the range, pre-existing (not used for the verdict)" / 「範囲内の、もとからの問題（判定に使っていません）」
     - "Out of range, for reference" / 「範囲外の参考」
     - "Next steps — for the user (not to be posted)" / 「次の一手 — 利用者向け（投稿しない）」
   - If the final verdict, after the check below and the command gates in the main session, is `fail` or `indeterminate`, write the reason it stopped as one plain sentence in the part of the comment draft to be posted (decision 37; in e2e D7 it said only "stopped after 2 rounds", and the approver could read neither the reason nor whether the confirmer had checked). Do not write it when you changed the verdict to `pass`. Write the reason from the kind of `stopReason`; do not copy the `stopReason` text, keys, `repeat_of` numbers, or the reviewers' summaries or quotes. When it stopped for the same reason (`same reason failed twice`), follow that sentence with the fixed sentences below that apply, word for word, according to the `confirmations` answers below and the check's `fixedOutsideCommit` (every one that applies; count n as each item says).
     - One or more `present`: "A confirmer that did not know the fix confirmed in the current files that these remain (n findings)." / 「修正の前後を知らない確認役が、今のファイルで残っていることを確かめました（n 件）。」 n is the number of findings.
     - One or more `none`: "The confirmer gave no answer for n findings, so they are unconfirmed." / 「確認役の答えが無く、確かめられていない指摘が n 件あります。」 n is the number of findings.
     - A path in a `stopReason` key (`gate|path|category`) is in `fixedOutsideCommit` of the check for the round before the one it stopped at (the last of `rounds`) (decision 38): "However, the fix commits did not change n of these files, so they may not have been worked on." / 「ただし、n 件のファイルは修正のコミットが変えておらず、直そうとされていない可能性があります。」 n is the number of such paths (without duplicates), not of findings. In this case the stop sentence must not say "fixed but it did not work"; say "remained after the fix".
   - If the final verdict is `fail` or `indeterminate`, put a section "Remaining findings (blocking the merge)" in the part to be posted, and list every finding in `remaining` whose `severity` is `blocking` and whose key (`gate|path|category`) is in the last round's `rounds[].keys` (decision 41; in e2e D8 the section had only `client.py:43`, and of the other four blocking findings in the verdict, two were listed under "In the range, pre-existing (not used for the verdict)" below and two were listed nowhere). With `pass`, `keys` is empty, so there is no such section. When there is nothing to list, as when the check or the command gates in the main session changed the verdict to `fail`, leave the section out and write the failing gates as their item says. Several perspectives raise the same problem, so merge findings by path and summary. Add the following fixed sentence, word for word, to a merged item only when both conditions below hold.
     - "This finding is on lines this change did not touch. It may predate the change." / 「この変更が触れていない行への指摘です。変更の前からある問題かもしれません。」
     - Condition 1: every `remaining` item before merging is in the check's `introducedOnUnchangedLines` below with the same gate, path and line, as an item of the last round (`remaining` items carry no round).
     - Condition 2: the line written in the comment draft (checked against the real file) is the same as the line of that `introducedOnUnchangedLines` item. The check judged "not touched by the change" on the line the reviewer gave, so if the checked line differs, the fixed sentence is not necessarily true (the line-number error of decision 30).
     - When only some of the items before merging are in `introducedOnUnchangedLines`, or condition 1 holds and condition 2 does not, do not add it; instead write the item, and the condition that failed (the gate and line of the items that fell out), in the report to the user and in the "Next steps" section. Items with none in `introducedOnUnchangedLines` get nothing added.
   - Take the fixed findings from `rounds[].fixedFindings` (decision 34). These are findings the fix agent reported as fixed, with gate, path, line and summary. They are a report, not a checked result, so write "reported as fixed" and make clear that the next round's reviewers and the check are what verified them. Several perspectives raise the same problem, so merge them by path and summary. The line is the number a reviewer gave in the file before the fix, so reviewers can disagree on it for a merged finding (in e2e D5, 37 and 38). In the comment draft, write the line checked in the fix commit's file (`git show <fix sha>:<path>`). For a finding that shows up in the check's `fixedOutsideCommit` (below), the commit did not change the file, so add "reported as fixed, but the fix commit did not change that file".
   - `indeterminate` means "could not decide", not a pass. Say so plainly.
   - `outOfRange` are findings on files outside the range (they appear when a perspective agent touched a referenced file, or when an optional `/code-review` gate compared against the local main). They are used neither for the verdict nor for fixing. Add only their count and summaries under the heading "Out of range, for reference".
   - If `outOfRangeBlocking` is 1 or more, findings a merge-blocking gate marked blocking went out of range. They may be findings whose path could not be normalized (seven in e2e D1), so whatever the verdict, put the count and those findings' paths and summaries at the **top** of the comment draft. If they point at a changed file in the range, ask the user to review the verdict. Count findings with the same gate, path and summary across rounds as one. `/code-review` findings go out of range before they get a severity, so they are not in this count (they are in `outOfRange`).
   - `preExisting` are findings on files in the range that a reviewer marked as predating the change (`origin: pre-existing`) (decision 33). They are used neither for the verdict nor for fixing. List them in the comment draft under the heading "In the range, pre-existing (not used for the verdict)" with path, line and summary. The same finding appears every round, so merge those with the same gate, path and summary into one. But leave out those with the same path and line as an item that got the fixed sentence in "Remaining findings" above (decision 41; in e2e D8, `client.py:11`, which another perspective marked `pre-existing`, was listed under this heading while correctness's `introduced` kept it in the verdict). The lines compared are both the lines checked against the real file for the comment draft. When the line of a `preExisting` item cannot be checked (`line` is `null`, or no matching line is found in the real file), list it rather than leaving it out. `preExistingBlocking` is how many of them a merge-blocking gate marked blocking. It is counted by the workflow including the items left out, so when writing a count in the comment draft, do not copy `preExistingBlocking`; count from the items listed.
   - `disputed` are findings a reviewer said came back after being fixed (`repeat_of`) and the confirmer could not find in the current files (decision 22). They are used neither for the verdict nor for fixing. Even on `pass`, do not drop them: list the path, the reviewer's claim and quote (`evidence`) and the confirmer's quote (`confirmerQuote`) side by side in the comment draft so a person can check. Missed problems show up here.
   - `confirmations` are every finding sent to the confirmer and its answer (decision 37). `answer` is `present` (still in the current files), `absent` (not found; these went into `disputed`) or `none` (no confirmer answer for that finding, such as an agent failure). `present` and `none` findings both stay in the verdict and count as repeats, so that round's loop always stops with "same reason failed twice". Only repeats of perspective gates go to the confirmer; repeats of gates compared by key (`/code-review` and command) do not. So in that `stopReason` sentence the numbers (`repeat of #N`) are attached only to perspective gates' keys, and the counts (`confirmer: N still present, M no answer`; counts of findings, not keys) are appended only when that round has one or more `present` or `none`. In the part to be posted, write only the fixed sentences above. Do not post the confirmer's quotes (`quote`) or the numbers; whatever the verdict, put them in the report to the user, and with `fail` and `indeterminate` also in the "Next steps" section. Treat `absent` ones as the `disputed` item above says.
   - `repeatMismatches` are blocking findings of failing gates whose `repeat_of` number points at a "reported as fixed" finding in another file (decision 35). They are not treated as repeats; they go into the verdict and the next fix as new findings. They are a sign that a reviewer got the number wrong and are not information for the PR's author, so do not put them in the part to be posted. If not empty, whatever the verdict (even `pass`), put the path, summary, given number and the file the number points at (`claimedPath`) in the report to the user. With `fail` and `indeterminate`, also put them in the "Next steps" section below. The same error can appear every round, so merge those with the same gate, path, summary and number into one. They also appear when a fix moved code to another file and the problem stayed where it moved, or when a reviewer shifted a number to point at another file's finding. A shift that points at another finding in the same file is treated as a repeat and does not appear here. (The moved-code and other-file cases are not treated as repeats, so the loop can run to the limit.)
   - `introduced` lists, with round numbers, the reviewers' findings on files in the range with `origin: introduced` (decision 36). They stay in the verdict and are the input for the check below. Do not report this list itself; report the check's `introducedOnUnchangedLines`.
   - `deferred` are command gates waiting to be run in the main session (decision 25). Settle them in "Running the command gates in the main session" below.
   - `notRun` are command gates not run because of `untrusted`. Say plainly "not run"; never write that they passed. If needed, the user checks the contents and runs again as `trusted`.
   - **Every time, check with git the diffs the reviewers read and the fix agent's reports (decision 19).** Do it whether `trusted` or `untrusted`, even with no fixes, because the round-1 diff file is also checked. Use the result file outside the repository written by `extract_result.py` in step 4 (inside the worktree it would leave an untracked file and stop `git worktree remove`), and run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/verify_fixes.py --base <start SHA> --start <HEAD recorded in step 4> --result <result> --diff-dir <diffDir>`.
     - On `status: mismatch` (a commit with no report, or a diff file missing or disagreeing with git), change the verdict to `indeterminate`: the reviewers read a diff different from the real one. Show the `invalid` reasons.
     - `notes` (file list disagreements) are added without changing the verdict.
     - `preExistingConflicts` are findings marked `pre-existing` whose line the change added or changed (decision 33). They cannot be said to predate the change, so leaving them out may have been wrong. The verdict does not change, but if not empty, whatever the verdict, put the count and the path, line and summary at the top of the report to the user and of the comment draft, and ask the user to review the verdict. Findings with shifted line numbers can show up too, so check against the real file before writing.
     - `introducedOnUnchangedLines` is the other direction (decision 36): reviewers' findings on files in the range marked `introduced` whose line the change neither added nor changed. In a diff that only deletes lines, the lines just before and after the deletion count as changed. The reviewer may have marked an existing problem `introduced` (in e2e D7, one reviewer that did not read the diff file marked four problems in the base that way). But problems the change exposed (properly `exposed`) and line-number errors show up too. The verdict does not change, and the findings stay in the verdict. This item is about the reviewers' classification, not information for the PR's author, so do not put it in the part to be posted. Those that meet the "Remaining findings" conditions above (blocking findings in the verdict) are listed there and get the fixed sentence when both conditions hold (decision 41). Items not in the verdict, such as nits, are not listed in "Remaining findings". If not empty, whatever the verdict (even `pass`), put the count and the path, line and summary in the report to the user. With `fail` and `indeterminate`, also put them in the "Next steps" section, so a person can decide whether that finding may fail the verdict. Merge those with the same gate, path and summary into one across rounds. Check the line against the real file before writing it.
     - `fixedOutsideCommit` are findings the fix agent reported as fixed (`rounds[].fixedFindings`) whose path that round's fix commit did not change (decision 38; e2e D7 observation 5). It hints that they were not worked on, but a correct fix of a cross-file mismatch made in the other file shows up too. Which is more common has not been seen in practice yet. Only the path is compared, so a wrong report naming another file the same commit changed does not show up here. The verdict does not change (the reason is decision 38 in `${CLAUDE_PLUGIN_ROOT}/docs/decisions.ja.md`). If not empty, whatever the verdict (even `pass`), put the round, path and summary in the report to the user. With `fail` and `indeterminate`, also put them in the "Next steps" section. Add the fixed sentence above to the part to be posted only when it bears on the stop reason (the note on the list of fixed findings is separate; per the decision-34 item above it is added whatever the verdict).
   - `unexpectedFiles` are fix commits that included files in neither the range nor the findings (in the fifth e2e run, a fix agent staged a session record that another plugin's hook had written). The workflow's value is built from the fix agent's report, so report the value from the check. It is not used for the verdict. Show the paths and ask the user whether to keep them or drop them from the fix commit.
   - **Running the command gates in the main session**: when one or more fixes went in, or `deferred` is not empty, run every command gate in the main session (those matching an `ask` rule run after the user's confirmation). Results from the second time on are the fix agent's own report, and deferred gates have no result at all.
     - If the verdict is `pass`, or `indeterminate` only because of deferral (stopReason "command gate(s) deferred to the main session"), change it to `pass` if all pass and to `fail` if any fails. Write the failing gates, and whether each was deferred or disagreed with the fix agent's report.
     - Leave `fail`, and `indeterminate` for any other reason, as they are; only add the results.
   - **PR body gates** (from step 2; decision 45). Apply them after the command gates above, to the verdict those leave:
     - A blocking gate whose check exited 1 changes `pass` to `fail`; one that exited 2 changes `pass` to `indeterminate`. `fail` and `indeterminate` stay as they are, with the results added. A non-blocking gate does not change the verdict.
     - In the part of the comment draft to be posted, write every failing gate (blocking or not) with the fixed sentence, word for word, followed by the `missing` and `empty` values the output lists: "The PR body lacks these sections, or they are empty:" / 「PR 本文に次の節が無いか、空です:」. For exit 2: "The PR body could not be checked." / 「PR 本文を確かめられませんでした。」. Never quote the body.
     - A gate not run (no PR, a GitLab MR, a value refused in step 2) goes in the report to the user with its reason, not in the part to be posted.
     - The fix agent cannot edit a PR body. The author (or the main session, on the user's word) fixes it with `gh pr edit <n> --body-file <file>`; then only `check_pr_body.py` needs to run again, not the whole review. With `fail` or `indeterminate`, say so in "Next steps".
   - Write the MR/PR comment draft to a temporary file outside the repository and show its path. Wait for an instruction before posting.
     - Check every line number in the comment draft against the real file before writing it. Reviewers sometimes give line numbers inside the diff file (decision 30; in e2e D2, a finding on line 11 of `client.py` got line 65). When the main session reads a diff file (`diff-r<N>.patch`), do not use its line numbers either (in e2e D5, the main session wrote line 42 of `diff-r1.patch` as the line of the fix on line 38 of `sync.py`). Line numbers are not used for the verdict, so a mismatch does not change it.
     - With `fail` and `indeterminate`, put a section headed "Next steps — for the user (not to be posted)" after the comment draft in the same file. It holds, for each remaining finding, what to fix; the stop reason; why the fix agent did not fix it (the text of `rounds[].fix.skipped`; findings on protected files show up here and not in `stopReason`, decision 32; when it stopped at the round limit, the last round has no `fix`, so say it stopped at the limit and check whether the remaining findings' paths are protected files in the three places above); what a person must decide before running again (whether to run the `untrusted` command gates, how to treat `disputed`, and so on); `repeatMismatches` and `introducedOnUnchangedLines`; items in "Remaining findings" that did not meet the conditions and got no fixed sentence (decision 41); `fixedOutsideCommit`; and the quotes and numbers of `confirmations`' `present` and `none` (if not empty; as each item above says). This section doubles as the correction plan (decision 29). Only the comment draft part is posted. On an `untrusted` PR, showing this section to the author would hand over material for your own judgement.
     - Write the comment draft about the target of the review (the PR/MR or branch). Do not tie it to another issue or task being worked on in the conversation by name or number (in e2e D2, the correction plan for a test seed got the conversation's issue number).
6. **Clean up**
   - After the check, whether `trusted` or `untrusted`, run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/write_allowlist.py --remove --diff-dir <diffDir>`. It removes the allowlist (if any) and the diff files (`diff-r<N>.patch`) in `<diffDir>`. The hook refuses an expired allowlist anyway, but do not leave it. The diff files are untracked, so leaving them stops `git worktree remove`. If `<diffDir>` has files the run did not write, the folder is kept. The hook's decisions are logged to `hook-decisions.jsonl` next to the allowlist (decision 27). Decisions whose git dir could not be found go to `${CLAUDE_PLUGIN_DATA}/hook-decisions.jsonl` with `cwd`, and decisions that could be written to neither end their reason with "This decision was not logged". To check the fix agent's refusals, look in these three places.
   - Leave the fix commits on the target branch; whether to push is the user's call.
   - Before deleting a throwaway branch or worktree, ask the user first if it needs `-D`.

## Scale (measured)

- Four perspectives × one pass: about 140k tokens per round (about 27–47k per perspective agent, Explore type, Sonnet).
  With the dedicated type `ccreview-reviewer`, one perspective agent's context at start is about 8–14k (the fifth e2e run; about 21k with the Explore type).
- With the default type, the fix agent took about 55k at start each time. With the dedicated type (`omitClaudeMd`), the spike's type took about 7.9k. The work's round trips come on top.
- In a measurement with eight hard-to-find seeded problems, the union of four perspectives × one pass found 8/8 in each of three trials. The built-in `/code-review` alone averaged 6/8, and the union of its three runs was 7/8.
- Even a small change costs well over a hundred thousand tokens per round, and several hundred thousand with fixes. Tell the user the estimate before running.
