# ccreview の設計判断

ccreview の設計判断と、その根拠になった検証の記録の要約です。
README、`skills/ccreview/SKILL.md`、コードのコメント、テストに出てくる「決定 N」（英語では "decision N"）は、下の「決定」の節の同じ番号の項を指します。
「e2e D5」「the sixth e2e run」「e2e session B」「spike 2」「open point I」などの呼び名は、「スパイク」「e2e の回と試験セッション」「論点」の節の同じ呼び名の項を指します。

決定は、決めた順に番号を振っています。
あとの決定が前の決定を改めたときは、前の項にその旨を書いています。
今の動作を知りたいときは、番号の大きい方を優先して読んでください。
数字や観察の元になった run の記録（transcript や結果の JSON）は、公開していません。

## 決定

### 決定 1: 正しさのレビューは組み込みの `/code-review` に任せ、投稿と合否の集約はメインが行う

正しさの判定を自前で作らず、組み込みの `/code-review` を使うと決めました。組み込みにレビュー本体・修正の適用・投稿まで揃っているためです。`--comment` は使わず、全ゲートの結果の集約と PR / MR への投稿は、メインのセッションが GitHub / GitLab の CLI で 1 回だけ行います。投稿を 1 回にまとめて合否を明示できること、認証が必要な場面で人を待てるのがメイン側だけであること、`--comment` の GitLab 経路は CLI を直接呼ぶので認証情報の受け渡しの仕組みを通らないことが理由です。のちに決定 11 で、既定の構成は観点別レビューに変わり、`/code-review` は任意のゲートに下がりました。

### 決定 2: 修正ループの上限と停止条件は、hook ではなく Workflow スクリプトで強制する

ループの上限と「同じ理由で 2 回連続して不合格なら止めて人に返す」は、Workflow スクリプト（JS）に決定的に書きます。hook だと状態ファイルが要って重くなり、スキルの指示だけでは構造としての強制になりません。Workflow の再開は同じセッションの中でしかできないので、セッションをまたぐ再開は Workflow では担いません。「同じ理由」は、言い回しが毎回変わるため文言では比べられず、構造化したキーで比べます。キーの中身は決定 6 のとおりです。のちに決定 15 で、「同じ理由」の判定そのものは観点役が行う形に改まりました。

### 決定 3: ゲートの宣言は `REVIEW.md` と `review-gates.yaml` の 2 本に分ける

文章で書く観点（重大度の定義、対象外のパス、リポジトリ固有のチェック）は、リポジトリ直下の `REVIEW.md` に置きます。コマンドと合格条件のような機械ゲートは `.claude/review-gates.yaml` に置きます。`REVIEW.md` は公式の慣習名なので、将来マネージド版のコードレビューを使うときも同じファイルが効きます。機械ゲートは LLM を通さずに決定的に判定したいので、yaml に分けました。yaml 1 本にまとめる案は、公式の `REVIEW.md` と二重になるため採りませんでした。のちに決定 32 で、この 2 つのファイルは修正 agent から編集できないよう守られました。

### 決定 4: `review-gates.yaml` の v1 は 7 キー・kind 3 種で始める

ゲートは `id`・`kind`（`command` / `review` / `perspective`）・`run`・`pass`（`exit0` / `no-blocking` / `max-findings:N`。決めた当時は `no-blocking` を `no-important` と呼んでいましたが、今のコードは `no-important` を知らない値として止まります）・`blocking`・`autofix`（`none` / `agent`）・`paths` の 7 キーで書きます。`perspective` の指示文は yaml に書かず、`ref` で `REVIEW.md` の節を指します。観点の本文の正を `REVIEW.md` に置き、決定 3 の二本立てを保つためです。

### 決定 5: 「宣言と検算」のゲートは、`kind: declare-verify` の枠だけ予約する

別に検討している「宣言と検算」の仕組み（候補の列挙は機械、再導出は別経路の検算者）をゲートに載せる場合に備え、`kind: declare-verify` の名前だけを予約しました。実装は、宣言の書式が決まってからです。今のコードはこの kind を受け付けません。

### 決定 6: 停止条件は 3 つのうちのどれか 1 つで、同じ理由のキーに行番号を入れない

次のいずれかで止めて人に返します。(1) 上限の 3 ラウンド（リポジトリごとに上書きできる）、(2) 同じキーが 2 ラウンド続けて不合格、(3) 不合格のキーの集合が前のラウンドより減らない（新しい退行を含む）。キーは `(gate_id, path, category)` で、行番号は入れません。修正で行がずれると同じ指摘が別の理由に見え、(2) が発火しなくなるためです。のちに決定 15 で、(2) と (3) の判定が改められました。

### 決定 7: 重大度と category は分類用の agent が付ける

`/code-review` を呼んだ agent の返す本文には、重大度も category も入っていませんでした（スパイク 3）。そこで、分類用の agent 1 体が各指摘に `severity`（`blocking` / `nit`）と `category`（`REVIEW.md` の語彙）を付けます。値はスキーマの enum で縛ります。command ゲートの失敗は、定義上 `blocking` に固定します。分類が欠けた指摘も `blocking` に倒します（fail-safe）。のちに決定 12 で、観点役が自分で重大度と category を付ける形になり、分類用の agent は観点役を通らない指摘にだけ使います。

### 決定 8: レビュー本文が返らなければ 1 回だけ再実行し、なお返らなければ「判定不能」で止める

`/code-review` の本文が返るかどうかは安定せず、3 回のスパイクで本文が返ったのは 2 回でした。そこで、本文が無いときは 1 回だけ再実行します。2 回目も無ければ verdict を `indeterminate` にして人に返します。「指摘 0 件」と「本文なし」を区別し、`indeterminate` は合格として扱いません。

### 決定 9: 読み取り専用の段は軽い agent で動かし、command ゲートは agent に実行させない

初回の e2e の消費を調べると、費用は「agent の数 × 起動時の文脈」で決まり、作業量にはほとんど依存しませんでした。最小の agent の起動時の文脈は、general-purpose 型で約 50k トークン、Explore 型で約 21k トークンで、差の約 29k は注入される CLAUDE.md と rules でした（2026-09-26 の実測。数字は計測したリポジトリの CLAUDE.md と rules の大きさによります）。そこで、分類・観点・command の予備実行を、CLAUDE.md を注入されない Explore 型で動かし、model も明示することにしました（Explore 型は model をセッションから継承して単価が上がったため）。command ゲートは、1 ラウンド目はスキルの事前チェックの結果を使い、2 ラウンド目以降は修正 agent がコミット後に実行した報告を使います。のちに決定 16 で観点役と分類役は Bash の無い専用の型に移り、決定 25 で Explore 型での command の予備実行は廃止されました。報告の欠けたゲートは「保留」になり、メインが確定します。

### 決定 10: 変更の範囲外のファイルへの指摘は、判定にも修正にも使わない

e2e 2 回目で、`/code-review` が種に含まれないファイルを指摘し、修正 agent がそれに従って範囲外のファイルを書き換えました。そこで、review と perspective の指摘のうち、変更ファイルに無いパスのものは `outOfRange` として報告するだけにしました。変更ファイルの集合は、修正のコミットが触ったファイルを足して増やします（修正が起こした回帰は拾うため）。command ゲートの指摘は除外しません。失敗した command の指摘を捨てると、失敗が `pass` に化けるためです。のちに決定 28 で、指摘のパスを変更ファイルに結び付ける処理と、範囲外に回った blocking の件数を知らせる `outOfRangeBlocking` が足されました。決定 33 では、範囲内のファイルにあるもとからの問題も判定から外しました。

### 決定 11: 既定の構成は観点別レビュー（4 観点 × 1 回）にし、`/code-review` は任意のゲートに下げる

観点は「正しさ」「セキュリティと秘密」「文書とリンク」「ファイル間の整合」の 4 つです。計測 2（見つけにくい種 8 件）では、`/code-review` の単発が 3 回で 5〜7 件、観点 4 つの和は 3 回とも 8 件でした。単発の見落としは繰り返しでは埋まりません。観点別は 1 回あたり約 140k トークンで、単発の約 90k より高く、観点 4 つを 3 回繰り返す構成の約 420k よりは安く済みます。`passes`（既定 1）で同じ観点を独立に複数回見ることもできます。決定 1 を改め、`kind: review` は残しますが既定の yaml ではコメントアウトしています。

### 決定 12: 重大度と category は観点役が自分で付け、1 つでも blocking ならゲートは不合格

観点役の出力スキーマで、`severity` と `category` を enum の必須項目にしました。分類用の agent は、これらを持たない指摘（`kind: review` など）と、command の失敗にだけ使います。観点ごとに重大度の判定がぶれる（同じ種が blocking と nit に分かれた）ことは、「最も重い判定を採る」ことで合否に影響しない形にしました。計測では、どの種も少なくとも 1 つの観点が blocking と判定しました。決定 7 を改めるものです。

### 決定 13: 観点役にレビュー対象のコードを実行させない（まずはプロンプトで）

観点役には、読み取り専用の git・grep・ls だけを使うよう指示しました。しかし e2e 4 回目で、観点役 10 体のうち 2 体が Python を実行し、1 体は変更されたコードを読み込んで実行しました。プロンプトでの禁止は効かないと分かり、信頼できない PR にはこの方式を使わないことにしました。のちに決定 16 で、Bash を持たない専用の型に置き換えられ、構造的に止まりました。

### 決定 14: range はスキルが merge-base から作り、ローカルの `main` に頼らない

`/code-review` を呼ぶ agent が、渡した range ではなく、常に `git diff main...HEAD` を実行していたことが transcript から分かりました。ローカルの `main` が古いと、範囲の外の差分まで見てしまいます。そこでスキルが `git merge-base origin/<base> HEAD` の SHA を起点に `<SHA>..HEAD` を作って渡し、観点役はその range を使います。のちに決定 26 で、差分の受け渡しは、モデルが書き写す方式から、git がファイルに書き出し観点役が読む方式に変わりました。

### 決定 15: 「同じ理由」は観点役が判定し、振動は修正が触ったファイルの新しい指摘だけで数える

e2e 4 回目で、別の問題が同じ `(gate, path, category)` のキーに衝突し、「同じ理由が 2 回」と誤って止まりました。文字列のキーだけでは、「直っていない」と「同じ場所の別の問題」を見分けられません。そこで、修正 agent が直した指摘の番号を `fixed` で返し、2 ラウンド目以降の観点役が各指摘に `repeat_of`（直したはずの指摘の番号か null）を付けます。直したはずの指摘が再び出たときだけ「同じ理由が 2 回」で止めます。「集合が減らない」も、「修正が触ったファイルに出た新しいキーの数 ≥ 直した数」に改めました。command と `kind: review` は、これまでどおりキーで判定します。決定 6 を改めるものです。のちに決定 22 で、`repeat_of` で止める前に確認役が今のファイルで確かめるようになり、決定 35 で、`repeat_of` の番号が指す指摘とパスが同じ場合に限られました。

### 決定 16: 観点役と分類役は、Bash の無い専用の型 `ccreview-reviewer` で動かす

型の定義は、`tools: Read, Grep, Glob`・`model: sonnet`・`omitClaudeMd: true` です。e2e 5 回目では、観点役 15 体すべてがこの型で動き、Bash の実行は 0 回でした（e2e 4 回目は 10 体中 2 体が実行）。起動時の文脈は 1 体あたり約 8〜14k トークンです。観点役は git を実行できないため、差分は外から渡します。型が見つからないときは、観点のゲートを `indeterminate` にし、Bash を持つ型には戻しません（fail-closed）。決定 13 を置き換えるものです。のちに決定 26 で、差分の渡し方はファイル経由に変わりました。

### 決定 17: 修正 agent は自分が編集したファイルだけをパス指定で stage し、範囲外のコミットは結果で報告する

e2e 5 回目で、修正 agent が、別のプラグインの hook が作業ツリーに書いたセッションの記録を自分で `git add` してコミットしました。あわせて、署名なしでコミットしてから amend で署名を付け直していました。そこで指示に、編集したファイルだけを `git add -- <path>` で stage すること、`--no-gpg-sign` と `--no-verify` を付けないことを足しました。プロンプトの禁止は効かないことがあるので（決定 13）、range の変更ファイルにも直す指摘のパスにも無いファイルを、`unexpectedFiles` として結果に載せます。判定には使いません。のちに決定 19 で、`unexpectedFiles` は申告からではなく git から取る値に変わり、決定 24 で、range の外のファイルは hook がそもそも編集させなくなりました。

### 決定 18: 信頼モードを `trusted` / `untrusted` に分け、`untrusted` では修正 agent も command ゲートも動かさない

信頼できない PR では、command ゲートが PR のコードを実行すること、修正 agent が指摘文やファイル本文に仕込まれた指示で操られること、PR が宣言を書き換えてゲートを弱めること、が脅威です。スキルが `trusted` か `untrusted` を決めて `args.trust` で渡します。既定は無く、無ければ workflow は起動時に止まります。判定は、利用者の明示が最優先で、明示が無ければ、PR の作者が自分のログインと同じときなどだけ `trusted` です。`untrusted` では、宣言（`review-gates.yaml` と `REVIEW.md`）を base 側から読み、command ゲートは実行せず、修正 agent も起動しません。blocking の指摘があれば `fail`、無くても実行しなかった blocking の command ゲートがあれば `indeterminate` です。読み取り専用の観点役はそのまま動きます。e2e 6 回目の untrusted は、観点役 5 体だけで約 108k トークン、Bash は 0 回でした。

### 決定 19: 修正 agent の自己申告は、メインが git で検算する

修正 agent が返すコミットの数・SHA・ファイル・差分は、モデルが書き写したものなので、偽りや写し間違いがありえます。スクリプト `verify_fixes.py` が、workflow の起動前の HEAD と結果を受け取り、コミット数・各 SHA の実在・実際のファイル・差分（行末の空白だけの違いは同じとみなす）を git から取り直して見比べます。申告のないコミットや差分の食い違いがあれば、verdict を `indeterminate` に直します。次のラウンドの観点役が、実物と違う差分を読んだことになるためです。ファイル一覧の食い違いは報告にとどめます。信頼モードによらず効きます。e2e 6 回目の trusted では `status: ok` でした。

### 決定 20: ccreview は独立したプラグインにする

ccreview を、オーケストレーション用の別のプラグインのスキルとして同居させるか、独立させるかの判断です。そのプラグインへの依存が実際には無いことが決め手でした。ループは Workflow スクリプト、分離は agent の `isolation` という標準機能で足り、ほかのプラグインのカタログの型・スキル・hook を使っていません。当時すでに、約 400 行の workflow、専用の型、検算スクリプト、テストがあり、さらに修正 agent 用の PreToolUse hook を足す予定でした。同居すると実際には無い依存を作り、ccreview 専用の hook 規則がほかのプラグインの `hooks.json` に混ざります。「hook はそれを必要とするプラグイン側に置く」という方針とも合いません。切り出しは、修正 agent の Bash 許可リスト hook の形が決まってから行うことにしました（hook は決定 21 で決まりました）。hook の設計前に切り出すと、直後に構成が大きく変わるためです。

### 決定 21: 修正 agent は専用の型 `ccreview-fixer` で動かし、PreToolUse hook が run ごとの許可リストで Bash を allow / deny に決め切る

e2e 6 回目では、修正 agent が許可確認に当たり、利用者が承認するまで約 79 分止まりました。同じ仕組みで、修正 agent が操られる脅威も扱います。hook は入力の `agent_type` で修正 agent を見分けるので、専用の型を使います。許可リストはスキルが run ごとに、range・変更ファイル・展開済みの command ゲートから、作業ツリーの外に書き出します。許可するのは、`git add -- <変更ファイル>`、決まったメッセージの `git commit`、`git diff <range>`、`git status`・`log`・`show`、宣言された command ゲートとの完全一致だけです。リスト外は `ask` ではなく理由付きの `deny` を返すので、背景の workflow は止まりません。`&&`・`;`・`|`・`$(…)`・リダイレクトを含むコマンドと、コードの実行（`python -c`・`pytest` など）は許しません。hook が壊れたときは、修正 agent だけを fail-closed（`deny`）にし、ほかのセッションには影響させません。のちにスパイクで、hook の `allow` は settings の `ask` 規則に負けると分かり（決定 23）、Edit / Write も hook で絞る決定 24 と、決定 27 の判定の記録が加わりました。

### 決定 22: `repeat_of` で止める前に、「直した」一覧を見ていない確認役が今のファイルで確かめる

観点役が `repeat_of` を付けた blocking の指摘があるとき、止める前に確認役を 1 体だけ起動します。確認役には「直した」一覧を渡さず、指摘の主張と観点役が今のファイルから逐語で写した引用 (`evidence`) だけを渡し、Read と Grep で今の本文を確かめさせます。`stillPresent: false` の指摘は `disputed` として判定にも修正にも使わず、観点役と確認役の引用を並べて結果に載せます。`stillPresent: true` か、答えが無いときは、これまでどおり「同じ理由が 2 回」で止めます。読み違いの原因は「直した」一覧の文面への引きずられだったので、同じ一覧を見る観点役を増やすよりも、一覧を見ていない別の目で引用を照らすほうが原因を断てると判断しました。確かめるのは観点の `repeat_of` だけで、command ゲートと `kind: review` の繰り返しはキーで決まるので確認役は使いません。
のちに決定 35 が、確認役に回す条件を「`repeat_of` の番号が指す申告された指摘とパスが同じ場合」に限りました。決定 37 が、確認役の答えをすべて結果の `confirmations` に返すようにしました。

### 決定 23: 許可リストを書き出すとき、宣言された command ゲートを `ask` 規則と照らす

修正 agent の Bash を許可リストの hook で絞ると (決定 21)、hook の `allow` は settings の `ask` 規則に負けることがスパイクで分かりました。優先順は「hook の `deny` ＞ settings の `ask` 規則 ＞ hook の `allow`」で、許可リストの内側でも `ask` 規則に当たるコマンドは、背景の run で人の確認を待って止まります。そこでスキルが許可リストを書き出すときに、展開した command ゲートを、有効な settings (managed・user・project・local) の `permissions.ask` と照らし、当たるものは許可リストに入れず、理由付きの `notRun` にします。修正 agent がそれを実行しようとしても hook の `deny` で返るので、run は止まりません。hook は完全一致を照らすだけにして、settings を読むのはスキルの側だけにしました。プラグイン同梱の agent では `permissionMode` が無視されるため、agent 定義で回避する案は採りませんでした。

### 決定 24: 修正 agent の Edit / Write / NotebookEdit も hook で絞る。許可するのは worktree 内の range の変更ファイルだけ

Bash の許可リストだけでは、許可したコマンドが、編集できるファイルを経由して別のコードを呼びます。たとえば `.git/hooks/pre-commit` を書けば `git commit` が実行し、`.git/config` の `core.fsmonitor` を書けば `git status` だけで実行されます。hook 自身や許可リストも、絶対パスで書き換えられます。そこで編集系のツールも hook で判定し、パスを realpath で解決したうえで、worktree の内側にあり、許可リストの `files` (range の変更ファイル) に含まれ、実在するものだけを `allow` にします。`.git`・`.claude-plugin`・`.husky`、`.claude/` の下の settings・hooks・agents・workflows・skills・commands、hook 自身のプラグインのルート、command ゲートのスクリプト (`protected`) は、変更ファイルでも常に `deny` です。`protected` は展開前のゲートの `run` から取ります。展開後から取ると、文書の検査ゲートの `{files}` (直すべき文書) まで保護してしまうためです。代償として、range 外の古くなった文書を直す修正はできなくなり、`skipped` として人に渡ります。
のちに決定 32 が、守る一覧に rules・`CLAUDE.md`・`REVIEW.md`・ゲートの宣言を足しました。

### 決定 25: `ask` 規則に当たるゲートと報告の欠けたゲートは「保留」にし、出口で `indeterminate`、メインで確定する

2 ラウンド目以降、許可リストから外したゲート (決定 23 の `deferredGates`) と、修正 agent が報告しなかったゲートは、status を `deferred` にします。ループは止めず、不合格にも数えません。出口で `pass` になるところに blocking の保留が残っていれば、verdict を `indeterminate` にし、結果の `deferred` に載せます。`fail` は変えません。スキルは、修正が入ったとき、または `deferred` があるとき、command ゲートをすべてメインで実行して、`pass` または `fail` に確定します。保留だけで `pass` を返すと、メインでの実行をスキルが忘れたときに `pass` が通ってしまうので、忘れても合格にならない向きにしました。同じ理由で、Explore 型で command を予備実行する経路は廃止しました。Explore は hook の対象外で Bash を持つため、制限のない Bash が workflow に残るからです。代償は、保留のゲートの失敗が修正ループに戻らないことです。

### 決定 26: 差分は git がファイルに書き、観点役はそれを読む

差分をモデルが書き写すと壊れることがありました (e2e のセッション B で、修正 agent が返した `diff` が二重にエスケープされ、検算が `mismatch` になりました)。そこで、スキルが `<toplevel>/.ccreview` を絶対パスの `<diffDir>` として作り、1 ラウンド目の `git diff <range> --output=<diffDir>/diff-r1.patch` を書きます。2 ラウンド目以降は、修正 agent がコミットのあとに `diff-r<N+1>.patch` を同じ形で書き、許可リストにはこの完全な形だけを載せます。観点役は `diffDir` から組み立てたパスを Read します。`verify_fixes.py` は差分ファイルを `git diff` の実物と見比べ、無い・食い違うは `invalid` にして verdict を `indeterminate` に直します。置き場所を worktree の中にしたのは、観点役の Read を作業ツリーの中に収め、manual モードの確認で背景が止まるのを避けるためです。`<diffDir>` に空白・引用符・シェルのメタ文字があるときと、シンボリックリンクのときは `write_allowlist.py` が拒否します。後片付けは `write_allowlist.py --remove` が差分ファイルと空の `.ccreview/` を消します。

### 決定 27: hook の判定を、fail-closed でも記録に残す

`CCREVIEW_GATE_BREAK` による故障が、許可リストのパスを決める前に例外を出すため、`deny` が `hook-decisions.jsonl` に 1 行も残らないことがありました (e2e のセッション C の欠陥)。`gate.py` は git dir を判定の `try` の外で先に求め、記録の書き先を 3 段にしました。1 つ目は `<git dir>/ccreview/hook-decisions.jsonl` です。2 つ目は git dir が求まらない・書けないときの `${CLAUDE_PLUGIN_DATA}/hook-decisions.jsonl` で、すべての記録に `cwd` を付けます。3 つ目はどちらにも書けないときで、`permissionDecisionReason` の末尾に「This decision was not logged: <理由>」と足し、修正 agent のツール結果として必ず残します。記録の失敗は例外の種類を問わず受け止めます。対になっていないサロゲート文字で書き込みが `UnicodeEncodeError` を出し、hook が出力なしで終わって fail-closed が破れる事例を再現したためです。許可リストの隣には、そのフォルダがあるときだけ書き (作らない)、`CLAUDE_PLUGIN_DATA` は絶対パスのときだけ使います。

### 決定 28: 指摘のパスを変更ファイルに結び付ける

`normalizePath` は「変更ファイルが指摘のパスで終わるか」しか見ておらず、観点役が worktree の絶対パスで返した指摘が変更ファイルと結び付かず、範囲外として外れていました (e2e D1 で、blocking の指摘 7 件が外れましたが、別の観点の相対パスの指摘に助けられて `pass` になりました)。この決定は 3 つの項からなります。
- **項 1**: workflow は、`diffDir` (`<toplevel>/.ccreview`) から worktree のルートを求め、指摘のパスがそのルートで始まれば外します。
- **項 2**: 指摘のパスから git の `a/` `b/` の接頭辞と `./` を外し、別のルートの絶対パス (main の checkout など) は、そのパスで終わる変更ファイルのうち最も長いものに結び付けます。相対パスにはこの逆向きの一致を使いません (`docs/x.md` と `x.md` は別のファイルです)。修正 agent が報告したファイルも、同じ正規化をしてから変更ファイルの一覧に足します。
- **項 3**: 結果に `outOfRangeBlocking` (マージを止めるゲートが blocking と付けた、範囲外の指摘の件数) を足します。判定は変えません (決定 10。範囲外の指摘を判定に使うと、ローカルの main と比べる `/code-review` の範囲外の指摘で落ちます)。スキルは 1 以上なら、判定にかかわらずコメント案の冒頭に件数・パス・要旨を載せ、範囲の変更ファイルを指しているなら判定の見直しを利用者に求めます。ゲート・パス・要旨が同じものは 1 件と数えます。

結び付けの誤りは、範囲外の指摘を範囲内に入れる向きにだけ起きるようにしました。関門は甘くならず、厳しくなる側に倒れます。

### 決定 29: 結果の出口をコメント案の 1 つにする

手順 5 のコメント案の保存先と、手順 6 の訂正プランの保存先が重なっており、e2e D2 で、メインが共有の checkout へ `cp -r` で書き出そうとしました。また、この 1 行が、他のプラグインとの唯一の結合でした。そこで手順 6 をやめ、`fail` と `indeterminate` のときは、コメント案と同じファイルの後ろに「利用者向け (投稿しない)」の見出しで「次の一手」を置きました。この節が訂正プランを兼ねます。メインが書き出すのは、手順で決めたもの (`<diffDir>`、許可リスト、リポジトリの外の一時ファイルの結果とコメント案) だけで、共有の checkout には書きません。コメント案は、会話の中で進めている別の issue やタスクに結び付けて名前や番号を付けません。プランやタスクとして残すかどうかと置き場所は、利用者が決めます。

### 決定 30: 指摘の行番号はファイルの行番号と指示する

e2e D2 で、観点役 4 つのうち 3 つが、差分ファイルの中の行番号をファイルの行番号として付けていました (ずれは差分ファイルの `@@` 見出しの行番号と一致しました)。観点役への指示にも schema にも、`line` が何の行番号かが書かれていませんでした。そこで、観点役への指示に「`line` はファイルそのものの行番号で、差分ファイルの行番号ではない。差分で問題を見つけたら、そのファイルを Read して表示された行番号を書く。ファイルや行がもう無ければ null」と足しました。schema の `line` の説明は、どの使い手にも当てはまる中立の文にして、「Read で取る」は観点役のプロンプトだけに置きます。さらに SKILL.md の手順 5 に「コメント案に載せる行番号は、実物のファイルで確かめてから書く」を足しました。行番号は判定に使っていないので、食い違っても判定は変わりません。

### 決定 31: `.claude/` の下の確認は受け入れて案内する。観点役の読み方は変えない

Claude Code の保護されたパスにより、`.claude/` の下の編集は、hook が `allow` を返しても manual モードでは人の確認が出ます。settings の allow 規則でも外せません。この確認は受け入れ (A1)、SKILL.md の手順 3 に、range に `.claude/` の下のファイルがあるときは起動の前にモードごとの扱いを利用者に伝えると書きました。dontAsk で拒否されるのは個々の編集で、修正 agent はその指摘を飛ばして残りを直します。もう 1 つの論点 (C) は、観点役の多くが差分ファイルを読まないことでした。変更されていない行にもとからある問題を blocking として挙げる害は、証拠がなかったため、観点役の読み方は変えず (C1)、次の e2e で挙がるかを確かめることにしました。e2e D3 では挙がらなかったので閉じました。
のちに e2e D4 で、もとからの問題の害が実際に出ました。これには決定 33 が答えています。

### 決定 32: rules・CLAUDE.md・ゲートの宣言を修正 agent から守る

`gate.py` の守る一覧 (`PROTECTED_GLOBS`) に、`.claude/rules/*` と `*/.claude/rules/*`、どの階層の `CLAUDE.md`・`CLAUDE.local.md`、`REVIEW.md`、`.claude/review-gates.yaml` を足しました。PR がもともと変えていても、修正 agent は編集も `git add` もできません。修正 agent は、自分を縛るルールや、自分の直しを判定する基準 (観点の本文とゲートの宣言) を書き換えてはいけないからです。断られた指摘は `skipped` に書かれ、`remaining` を通して判定が `fail` になり、メインのセッション (人の確認の下) に戻ります。`REVIEW.md` と `review-gates.yaml` は ccreview が根元から読むので、根元のものだけを守ります。e2e D4 で、守るファイルの Edit が `deny` になり `skipped` に入り、`remaining` でメインに戻ることを確かめました。

### 決定 33: もとからの問題は判定にも修正にも使わない

e2e D4 で、変更が触れていないもとからの問題 (コードと README) が blocking で挙がって `fail` になり、修正 agent が PR の範囲を広げました。そこで観点役は、指摘ごとに必須の `origin` を付けます。判定は 1 つの問いで決めます。「この変更 (修正のコミットを含む) を元に戻しても、この問題はまったく同じ形で残るか」。残るなら `pre-existing` とし、判定にも修正にも使わず、結果の `preExisting` に載せて人に見せます。残らないなら判定に入れ、変更が足した問題は `introduced`、土台では正しかったのに変更で誤りになった問題は `exposed` と付けます。迷ったら判定に入れる側に倒し、`origin` が無いもの、知らない値、観点以外のゲートの指摘は判定に入れます。問いの定義は REVIEW.md ではなく workflow のプロンプトに置きます。PR の側から弱められないようにするためです。結果の `preExistingBlocking` は、blocking と付けられた `pre-existing` の件数です。`verify_fixes.py` は、`pre-existing` とされた指摘の行が、その巡が読んだ状態で変更が足した・変えた行に入っていないかを `git diff -U0` で見て、入っていれば `preExistingConflicts` に返します。判定は変えず、スキルが利用者に見直しを求めます。
のちに決定 36 が、逆の向き (`introduced` なのに変わっていない行) の報告を足しました。

### 決定 34: 直したと申告された指摘を `fixedFindings` で返す

e2e D5 で、コメント案に書かれた行番号が、実際の行ではなく差分ファイルの行番号になっていました。SKILL.md には「実物のファイルで確かめる」という決まりがありましたが、結果の JSON に直した指摘のパスと行が無く、メインには差分ファイルのほかに行番号の出どころがありませんでした。そこでループは、ラウンドごとに修正 agent が「直した」と申告した指摘 (`claimedFixed`) を、ゲート・パス・行・category・要旨で `fixedFindings` に返します。修正が無かった回やコミットしなかった回は `[]` です。申告であって確かめた結果ではありません。SKILL.md の手順 5 では、`fixedFindings` から「直したと申告した」指摘を取り、同じ問題はパスと要旨で 1 件にまとめ、行は修正のコミットのファイル (`git show <sha>:<パス>`) で確かめて書きます。workflow のスクリプトは git を実行できないので、ループが行を計算する案は採りませんでした。同じ変更で、`gate.py` の `git add` の拒否の文を整理し、守るファイルには Edit と同じ文を返すようにしました。

### 決定 35: `repeat_of` の番号を、申告された指摘のパスと照らす

決定 22 のあとも、観点役が申告されていない指摘に範囲内の `repeat_of` を付けると、誰も直そうとしなかった指摘について「fix did not hold」と止まり、確認役も 1 回むだに呼ばれることを、loop-sim で確かめました。そこで `isRepeat` は、観点のゲートの指摘について、番号が範囲にあることに加えて、その番号の指摘 (`claimedFixed[repeat_of - 1]`) とパスが同じことを求めます。合わなければ繰り返しではなく新しい指摘として扱い、確認役にも同じ理由の停止にも回さず、次の修正に渡します。照らすのはパスだけです。「直した」一覧は全観点に同じ番号で見せる 1 本の一覧なので、別の観点の指摘の繰り返しは正当です。カテゴリは観点役ごとに付け方が違い、行は修正で動きます。番号が別のファイルを指した指摘は、判定を止めうるもの (落ちたゲートの blocking) に限り、結果の `repeatMismatches` に載せます。観点役の番号の誤りの報告なので、コメント案の投稿する部分には載せません。損は、本物の繰り返しの番号を観点役が 1 つずらしたときなどに、止まらずに上限まで回ることがある点ですが、判定は誤らず、`repeatMismatches` に出ます。
のちに決定 37 が、止まった理由の文に `(repeat of #N)` を足しました。

### 決定 36: `introduced` なのに変更が触れていない行を、検算で報告する

決定 33 は「迷ったら判定に入れる」と決めたので、もとからの問題に `introduced` が付くと判定に入りすぎます。e2e D7 で、差分ファイルを読まなかった観点役 1 体が、土台の問題に `introduced` を付けました。そこでループは、範囲内の観点の指摘のうち `origin` がちょうど `introduced` のものを、回の番号付きで結果の `introduced` に返します。`verify_fixes.py` は、その指摘の行を `git diff -U0` と照らし、変更が足しても変えてもいない行のものを `introducedOnUnchangedLines` として返します。判定は変えません。行を消しただけの差分では、消した位置の前後の行を変えた行と数えます (消したことで生じた問題はそこに出るため)。この数え方は、この検査だけに使います。報告は利用者への報告と、`fail` と `indeterminate` の「次の一手」に載せ、観点役の分類の話なので、コメント案の投稿する部分には載せません。観点役に差分の逐語の引用を求める案 (I2) は、この報告にもとからの問題への `introduced` が繰り返し出たときの次の段に置きました。

### 決定 37: 確認役の答えをすべて結果に返し、止まった理由をコメント案に 1 文で書く

確認役 (決定 22) の答えのうち、結果に残るのは「無かった」だけでした。「残っている」と「答えが無い」はどちらも判定に残って止まり、結果にもログにも残らず、止まった理由の文も同じになります (e2e D7 で、確認役が動いたことが投稿する部分から読み取れませんでした)。そこでループは、確認役に回したすべての指摘を、回・ゲート・パス・行・要旨・`repeat_of`・`answer` (`present` / `absent` / `none`)・確認役の引用とともに、結果の `confirmations` に返します。判定は変えません。「same reason failed twice」の理由の文には、キーごとの `(repeat of #N)` と、その回の `present`・`none` の件数 (`; confirmer: N still present, M no answer`) を足します。最終の判定が `fail` か `indeterminate` のときは、コメント案の投稿する部分に、止まった理由を平易な 1 文で書きます。同じ理由で止まったときは、確認役の答えに応じて SKILL.md の定型文を、文言を変えずに続けます。`stopReason` の英文・キー・番号・観点役の要旨や引用は、`untrusted` の PR の作者がファイルに仕込んだ文が入る余地を減らすため、投稿しません。
のちに決定 38 が、修正のコミットがそのファイルを変えていないときの定型文を足しました。

### 決定 38: 修正のコミットが変えていないファイルへの「直した」申告を、検算で報告する。判定は変えない

修正 agent が直していない指摘を `fixed` に入れると、「直そうとして直らなかった」と読める理由の文が出ます。`fixed` の申告はどこでも照らしていませんでした。`verify_fixes.py` は、結果の `rounds[].fixedFindings` のうち、そのパスをその回の修正のコミット (`git diff-tree`) が変えていないものを、`fixedOutsideCommit` として返します。workflow が作っていないコミットは `invalid` として扱うので、その回は見ません。

**判定を変えない理由**: ファイル間の食い違い (README の記述とコードなど) は、相手側のファイルを直して解消することがあり、それは正しい修正でも `fixedOutsideCommit` に出ます。照らした結果は「直そうとされていない手がかり」であって、証明ではありません。照らすのはパスだけなので、同じコミットが変えた別のファイルのパスを書いた誤りの申告は見逃します。証拠の無いまま判定の挙動を変える案 (申告を `claimedFixed` から外す) は、相手側の修正まで外れ、同じ指摘がまた出ても繰り返しと分からなくなるので採りませんでした。

報告は、判定にかかわらず利用者への報告に載せ、`fail` と `indeterminate` では「次の一手」にも載せます。止まったキーのパスが、止まった回の 1 つ前の回の `fixedOutsideCommit` にあるときだけ、コメント案の投稿する部分に定型文を足し、止まった理由の 1 文も「直したが効かなかった」ではなく「修正のあとも残った」と書きます。計算は検算の側に置きました。workflow は git を使えず、修正 agent の `files` は自己申告で、照らす相手にならないためです。

### 決定 39: 1 つの観点だけが担う型は、観点役を増やさず今の構成に任せる

秘密の直書きと文書リンクの意味は、計測 2 ではほぼ 1 つの観点だけが挙げていました。そのため、その観点の 1 体が見落とすと、全体で見落とすおそれがありました。一方、e2e 6 回目以降の記録のある回では、複数の観点が秘密を挙げています。REVIEW.md の「観点の外の問題に気づいたら、報告してかまいません」が効いたためと見ていますが、確かめてはいません。観点役を増やさず (`passes` も観点の数も今のまま)、REVIEW.md の文言も変えないことにしました。REVIEW.md に「秘密はどの観点でも報告する」と書く案は、今の文章と同じ種類で、効いたかを測るには新しく秘密を入れる種が要ります。security を `passes: 2` にする案は、1 ラウンドごとに agent が増えるのに、重なりがすでに出ているため、費用に見合う根拠が弱いです。秘密を決定的な検査 (`kind: command` のゲート) で見る案は、別の論点として残しました。

### 決定 40: 観点役のプロンプトで差分の節を先に置き、`introduced` を差分の行に結び付ける

e2e D7 と D8 で、土台の行に `introduced` を付けたのは、どちらも 2 巡目に差分ファイルを読まなかった観点役 1 体でした。プロンプトを確かめると、変更ファイルの指示が `## Diff` の節より前にあり、差分ファイルの指示には「Read ... first」のあとに「ファイルが無ければ変更ファイルを読め」という逃げ道の文が付いていました。並び順が原因というのは見立てで、確かめてはいません。そこで `## Diff` の節 (差分ファイルの指示、行番号の決まり、差分が古いときの注記) を変更ファイルの指示より前に置き、文言を「Read `diff-rN.patch` before any other file」にしました。逃げ道の文は、スキルの準備が失敗して差分ファイルが無い場合の安全網として、「Only if that file does not exist」と狭めて残しました。`origin` の `introduced` には、差分ファイルがあるときは、問題の原因の `+` か `-` の行を差分の中で見つけてから付ける、と足しました。引用を出力させるわけではありません (I2 ではありません)。観点役の型 (`agents/ccreview-reviewer.md`) も、差分ファイルを先に読む書き方にしました。I2 に進む条件は、この変更のあとも、検算の報告に差分を読まなかった観点役の誤った分類が出たときと読み替えました。

### 決定 41: 判定に入った指摘は「残った指摘」にすべて載せ、変更が触れていない行のものには事実の 1 文を添える

e2e D8 で、判定に入っている blocking の指摘のうち、`client.py:43` 以外は投稿する部分から消えるか、「もとからの問題 (判定に使っていません)」に載っていました。投稿する部分だけを読むと、1 件を直せば通るように読めますが、判定は `fail` のままのはずでした。`fail` と `indeterminate` のとき、投稿する部分に「残った指摘 (マージを止めるもの)」の節を置き、`remaining` のうち `severity: blocking` で、キーが最後の回の `rounds[].keys` にある指摘をすべて載せます。同じ問題を複数の観点が挙げるので、パスと要旨で 1 件にまとめます。まとめた項に、次の 2 つの条件をどちらも満たすときだけ、定型文「この変更が触れていない行への指摘です。変更の前からある問題かもしれません。」を、文言を変えずに添えます。(1) まとめる前の `remaining` の項のすべてが、`introducedOnUnchangedLines` に、ゲート・パス・行が同じで最後の回の項としてある。(2) コメント案に書く、実物で確かめた行が、その項の行と同じ。条件を満たさない項は添えず、利用者への報告と「次の一手」に書きます。定型文を添えた項と同じパス・行の `preExisting` は、「もとからの問題」に載せません。「確かめ中」のような状態の言葉は、投稿したコメントが変わらないので使いません。決定 36 の分類の報告は、今までどおり投稿しません。

### 決定 42: workflow の出力ファイルからの結果の取り出しをスクリプトに固める

e2e D8 で、workflow の完了の通知の `<result>` が切れており (先頭 8,000 字のあと「truncated」)、run のセッションが出力ファイルを読む形を自分で組み、`cd` と相対パスのコマンドが許可の確認になって、人が戻るまで約 6 時間待ちました。取り出しは入力が同じなら毎回同じ答えになるので、スクリプトの仕事です。`scripts/extract_result.py --output <通知の output-file の絶対パス> --out <リポジトリの外の一時ファイルの絶対パス>` を足しました。出力ファイルの `result` (object でも JSON の文字列でもよい) を取り出して `--out` に書き、標準出力には `verdict`・`stopReason`・回数・手順 5 が読む一覧の件数だけを出します。形が違う、JSON でない、入れ子が深すぎる、ファイルが無い、パスが相対、`--out` がリポジトリの中か `--output` と同じか書けない、のいずれかでは、何も書かずに終了コード 2 で止まります。理由にはキーの名前だけを出し、値は出しません (要旨や偽の認証情報の文字列が入りうるため)。SKILL.md の手順 4 の終わりに「結果を受け取る」項を足し、通知の絶対パスをそのまま渡すこと、`cd` も相対パスも使わず自分で読み方を組まないこと、終了コード 2 のときは理由を利用者に伝えて回り込まないことを書きました。出力ファイルの形はハーネスの内部の形なので、頼る場所をこのスクリプト 1 つにして、形が変われば分かる言葉で止まるようにしています。

### 決定 43: workflow の agent に依頼文が渡る件は、運用で済んだと記録する

workflow の agent には、起動したセッションの利用者の発言が `[Workflow harness — user request]` の枠で中継されます。run 24 本の記録を数えると、利用者の発言で始まったターンで呼んだ run は 21 本すべてで中継があり、中継が無かった run は、裏の作業の完了の通知で始まったターンで呼んだ 2 本だけでした。「ハーネスの挙動が途中で変わった」という以前の見立ては記録と合わなかったので、取り消しました。e2e D1〜D8 で中継されていたのは起動のコマンドだけで、PR の作者が中継に差し込む経路は見つかっていません。修正 agent の安全の境界はもともとプロンプトではなく、hook の許可リストとその fail-closed (決定 21・23・24・27) に置いており、`untrusted` で修正 agent を起動しないこと (決定 18) も中継では変わりません。そこで ccreview のコードは変えず、e2e では起動の発言をコマンドと引数 (ブランチ・base・信頼モード) だけにし、段取りと期待は run のあとでリポジトリに入れる運用にしました。実際のレビューで `/ccreview` に書き足した言葉は、起動した人 (マージを決める人) の意図として受け入れます。通知のターンで呼べば中継を避けられる案は、中継の有無を決める規則が記録から推したもので文書で確かめていないため、採りませんでした。

## スパイク（小さな確かめ）

### スパイク 1: 組み込みの `/code-review` を workflow の agent から呼べるか（spike 1）
workflow の agent から `/code-review` を呼ぶと、同期的に最後まで動き、エラーも拒否も出ませんでした。パスだけを渡すと、そのパスの未反映の差分が対象になり、ファイル全体の監査にはなりませんでした。このため、ゲートの `review` には必ず差分の範囲を渡します。ただしこの回は、レビュー本文が返りました。→ 決定 1・2

### スパイク 2: 分離 worktree の中で `--fix` を動かす（spike 2）
`isolation: 'worktree'` の agent で `--fix` つきの `/code-review` を動かすと、変更は分離 worktree の中だけに収まり、呼び出し元への漏れはありませんでした。ただしこの回は、レビュー本文が返らず、重大度（severity）も `null` でした。本文が返らない原因は `--fix` だと見ていましたが、スパイク 3 で否定されました。判定のラウンドは `--fix` なしにし、修正は別の段に分けます。→ 決定 7

### スパイク 3: `--fix` なしでも本文が返らないか（spike 3）
`--fix` なしで low と medium を並列に動かしました。low は本文が返らず、medium は本文が返りました。3 回のスパイクを通して、本文が返ったのは 3 回中 2 回です。つまり、本文が返るかどうかは `--fix` と関係なく不安定です。medium の本文は種のバグ 3 件をすべて見つけましたが、重大度と category は含みませんでした。本文なしは合格と読まず、1 回だけ再実行してから「判定不能」にします。判定用の `review` の既定は medium です。→ 決定 7・8

### range の取り違えを確かめたスパイク（range-scope spikes）
`/code-review` が指定した範囲の外のファイルを指摘する原因を調べました。呼び出し先の `/code-review` は、渡した範囲の引数を使わず、いつも `git diff main...HEAD` を実行していました。ローカルの `main` が古かったため、範囲外の指摘だけが返り、範囲内の不具合は見落とされました。上流のブランチを base に向けても同じでした。変更ファイルのパスを対象に渡すと、範囲内の指摘だけが返りました。範囲の起点は、ローカルの `main` ではなく merge-base から作ります。→ 決定 14

### 決定 21 のスパイク（decision-21 spike）
使い捨てのプラグインで、専用の型・PreToolUse hook・workflow を作り、背景の workflow から 3 回動かしました。分かったことは 4 つです。一つ目は、hook の `deny` は settings の `ask` 規則にも `allow` 規則にも勝つことです。二つ目は、hook の `allow` は `ask` 規則に負けることです（`ask` 規則に当たるコマンドは、hook が許しても利用者の確認が出ます）。三つ目は、`deny` の理由が agent に届き、agent はやり方を切り替えることです。四つ目は、プラグインに同梱した agent 定義でも、`omitClaudeMd` と `tools` が効くことです。許可リストの外を `deny` にすれば背景の run は止まりませんが、許可リストの内側でも `ask` 規則に当たるコマンドは人を待って止まります。→ 決定 21・23

## 論点（open point）

### 論点 G（open point G）
保護されたファイルの指摘だけが残った回は、修正 agent を呼んでも何も直せず、呼び出しがむだになります。D5 で、この形が混ざらずに出ました（2 ラウンド目に修正 agent を 1 回むだに呼び、`fix agent made no commit` で止まりました）。決定 33 では扱わず、そのままにしました。

### 論点 H（open point H）
もとからある問題が、判定にも修正にも入ってしまうことです。D4 で、ラウンド 2・3 に出た古い問題が `fail` と範囲の広がりを招きました。→ 決定 33

### 論点 I（open point I）
`introduced` と付いた指摘が、変更が足しても変えてもいない行を指す場合です。D7 で、差分ファイルを読まなかった観点役 1 体の誤りとして出ました。誤る向きは判定に入れすぎる側で、害は出ませんでした。観点役の分類を変えず、検算が `introducedOnUnchangedLines` として報告します。判定は変えません。→ 決定 36

### 論点 J（open point J）
観点役が付ける `repeat_of` の番号が、「直した」と申告された指摘と照らされていませんでした。別のファイルの指摘を指していても確認役に回り、誰も直そうとしなかった問題について「直したが効かなかった」と書かれて止まりました。読解だけで予測した問題で、D7 の写しの run ではこの形が出うることを確かめました。`repeat_of` の番号が指す指摘とパスが同じ場合だけ繰り返しと見なします。合わないものは新しい指摘として次の修正に回し、`repeatMismatches` に報告します。→ 決定 35

### 論点 K（open point K）
差分ファイルを先に読ませる（決定 40）と、もとからある問題の報告が減るかもしれないことです。D9 で、D6〜D8 では報告されていた土台の行の不具合が、どの観点役からも出ませんでした。ただし D9 では、変更ファイルの全体を読んだ観点役もこの行を挙げていないので、全体を読ませれば戻るとは言えず、原因は分けられていません。もとからある問題は判定に使わないので、ゲートの正しさには響きません。1 回だけの観察なので、まだ何も変えていません。次の run でも同じ形が出たら、扱いを決めます。
